## 1. 概要

コンサルタント・講師（あなた）が、Claude Codeで「〇〇さんの広告設計書を作って」と頼むと、Claudeがヒアリングしながらブランド情報を整理し、広告設計書をファイルに保存する仕組みです。

- 形式：Claude Codeの **Skill**（Claudeに作業手順を覚えさせる説明書のようなもの）
- 置き場所：このリポジトリの `.claude/skills/ad-plan/`
- 追加の費用やサーバーは不要

## 6. 利用の流れ

**新しく作る場合**
1. あなたがClaude Codeで「hana salonの広告設計書を作って」と頼む
2. Claudeが、すでに分かっている情報を整理する。ヒアリングメモやLPの文章などを貼れば、そこから読み取る
3. 足りない必須項目だけを、**1回につき最大3問**、おすすめ案付きで質問する
4. 必須項目がそろったら（またはあなたが「お任せ」と言ったら）初稿を作る
5. Claudeが、共通編の「出力の品質基準」で自己チェックし、直せるところは直す
6. 設計書を `output/ad-plans/{日付}_{ブランド名}.md` に保存し、要点をチャットに表示する
7. 「修正しますか？」と確認する

**修正する場合**
- 「コピーをもっと上品に」「ストーリー型を2案にして」などと伝えると、同じファイルを更新する。更新前の内容は `output/ad-plans/_old/` に残す

**入力不足の場合**
- 必須項目が足りなくても、初稿は作る。足りない部分は「10. このツールが仮定したこと」に書き、質問を続ける

## 8. 機能要件

### 機能1：情報の整理
- 貼り付けられた文章（ヒアリングメモ、プロフィール、LPの文章など）から入力項目を読み取る
- 「決まっていること／仮定したこと／確認が必要なこと」に分けて表示する

### 機能2：ヒアリング
- 足りない必須項目を、広告の結果に大きく影響する順に質問する
  - 優先度：①広告の目的とクリック先 ②理想のお客様と悩み ③強み ④世界観 ⑤予算
- 1回の質問は最大3問。それぞれにおすすめ案を付ける
- すでに答えた内容は聞き直さない

### 機能3：広告設計書の作成と保存
- 共通編の構成（1〜10章）どおりに作成する
- 保存先：`output/ad-plans/{YYYYMMDD}_{ブランド名}.md`
- 同じ名前のファイルがあるときは、上書きせず `_2` を付ける

### 機能4：自己チェック
- 共通編の「出力の品質基準」と「表現チェックの基準」で確認する
- チェック結果を設計書の最後に一覧で付ける

### 機能5：修正
- 修正の指示を受けたら該当する章だけを直し、何を変えたかを3行以内で伝える

## 10. データ設計（B版）

| データ名 | 保存先 | 備考 |
|---|---|---|
| 広告設計書 | `output/ad-plans/` | クライアント情報を含むため、**GitHubには上げない**（`.gitignore` に追加） |
| 修正前の版 | `output/ad-plans/_old/` | 同上 |
| Skill本体 | `.claude/skills/ad-plan/SKILL.md` | GitHubで管理してよい（クライアント情報を含まない） |
| 設計書の型・基準 | `.claude/skills/ad-plan/` 内 | A版と同じ内容を使う |

## 13. エラーと例外

| 状況 | Claudeの動作 |
|---|---|
| ブランド情報がほとんどない | 「ブランドの世界観を決める3つの質問」から始める |
| 入力に効果の言い切りなど注意表現がある | 設計書には使わず、「8. 表現の注意点」で指摘して言い換え案を出す |
| 入力どうしが矛盾している（例：上品な世界観なのにカジュアルな言葉づかい） | どちらを優先するか、1問だけ確認する |
| 保存フォルダがない | 自動で作る |
| 同じ名前のファイルがある | `_2` を付けて保存し、その旨を伝える |
| 頼まれていないのに実装やWeb検索を始めそうになる | 行わない。設計書の作成だけに留める |

## 15. 技術構成案

| 技術 | 役割 | 理由 |
|---|---|---|
| Claude Code Skill（`SKILL.md`） | 手順・質問ルール・出力の型をClaudeに読ませる | ファイル1〜3個で作れ、あなたが文章で直せる |
| Markdownファイル | 設計書の保存 | そのままNotionやGoogleドキュメントに貼れる |

- A版とB版で、設計書の型と品質基準を**同じファイルから読む**ようにし、片方だけ古くなるのを防ぐ（実装時に置き場所を決める）

## 17. テストケース

| テスト名 | 事前条件 | 操作・入力 | 期待される結果 | 確認方法 |
|---|---|---|---|---|
| 正常：メモから作成 | ヒアリングメモあり | メモを貼って「広告設計書を作って」 | 不足項目だけ質問され、回答後に設計書が保存される | 実際に試す |
| 正常：お任せ | — | 質問すべてに「お任せ」 | 仮定が明記された設計書ができる | 実際に試す |
| 異常：情報がほぼない | — | 「サロンの広告を作りたい」だけ | 世界観を決める質問から始まる。いきなり設計書を作らない | 実際に試す |
| 品質：NG表現 | — | 強みに「誰でも必ず月収100万」 | コピーに使われず、注意点に言い換え案が出る | 実際に試す |
| 修正 | 設計書1件あり | 「共感型をもっと上品に」 | 5章の共感型だけ変わり、旧版が `_old/` に残る | ファイルの差分を確認 |
| 重複 | 同日・同名のファイルあり | 同じブランドで新規作成 | `_2` 付きで保存される | ファイル一覧を確認 |
| 安全：GitHub | — | `git status` を実行 | `output/` が表示されない | コマンドで確認 |
